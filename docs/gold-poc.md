# Gold dimensional model — proof of concept

Status: **PoC under owner review** (October 2026). Design: the owner's doc "Gold dimensional
model — design draft 2" (Claude Docs) and `docs/model.md`. This page is the runbook and the
hand-over: anyone (or any model) continuing the work starts here.

## What it is

A small star built from **real samples of every cube source**, in the catalog namespace `poc`,
next to `gold`, so the owner can see the model as tables, use the metrics in a BI tool and
decide what becomes v1. Nothing in `gold` changed; the PoC is rebuilt in full by dbt
(`warehouse/models/poc/`, all under the 1 M-row policy, `warehouse.yaml full_rebuild`).

| Table (`poc.`) | One row is | Notes |
|---|---|---|
| `dim_calendar` | one day 1900–2100 | `gold.dim_date` + period labels, period-start flags; `date_key` is the date |
| `dim_geography` | one **area** | codes of every source as attributes (iso2, nuts_code, terc_code, bdl_unit_id, wb_code); Polish hierarchy Polska → makroregion → województwo → region → podregion → powiat → gmina; `country_key`, `wojewodztwo_key`, `powiat_key` for drill-down |
| `map_geography` | one source code → area | `_X` when unmatched; `build_check` counts them |
| `dim_unit`, `dim_frequency`, `dim_source`, `dim_observation_status` | code lists | |
| `dim_measure` | one measure | **the catalogue**: activated measures (from the samples) and every other block of the five sources from `gold.coverage` with its status (`not activated`, `waiting`, `published without data`…) |
| `measure_dimensions` | one measure × dimension | geography levels, time, each breakdown with its members (scenarios 2 and 3) |
| `dim_series` | one time series | measure × geography × breakdown; `is_total`, `sex_key`, first/last date, points |
| `fact_annual`, `fact_semiannual`, `fact_quarterly`, `fact_monthly`, `fact_daily` | one series × period | `date_key` = first day of the period; value, status, provenance |
| `dim_concept`, `concept_measures` | concept; concept × measure | from `warehouse/macros/poc_blocks.sql` (`poc_concepts`) |
| `metrics_population`, `metrics_gdp_current_prices`, `metrics_unemployment_rate`, `metrics_inflation`, `metrics_fx_rate` | concept × source × area × period | generated by `macros/poc_metrics.sql`; total series only, unmatched areas (`_X`) left out, geography and calendar attributes flattened (what a BI tool imports) |
| `src_eurostat`, `src_dbw`, `src_dbw_dictionary` | one Silver row | extraction stages (Python models): only the activated blocks' files, read through the Iceberg metadata |
| `build_eurostat`, `build_bdl`, `build_dbw`, `build_wdi`, `build_nbp`, `build_nbp_bop`, `build_nbp_interest_rates` | one observation | build stages (the per-block builder of v1), not for use |
| `build_check` | one activated block | rows, series, unmatched geography, unplaced periods, dates, flags; a block with no rows shows its catalogue status: read after every build |
| `grain_check` | one block with duplicate series × period | empty when the grain holds; `tests/poc_fact_grain.sql` fails otherwise |

Keys are natural strings so the model reads without lookups: `geography_key` `PL`, `TERC:1261011`,
`NUTS:PL91`, `BDL:<id>`, `EUROSTAT:EU27_2020`, `WB:WLD`; `measure_key`
`<source>:<block>:<unit>[:<measure codes>]`; `series_key` = `measure_key|geography_key|breakdown_json`.
v1 may switch to 64-bit hashes (design decision 4).

Measure rules of the PoC (to refine per domain in v1): Eurostat measure = dataset × unit × the
dimensions named in `poc_eurostat_measure_dims` (na_item, indic_de, indic_em); BDL measure =
subgroup × unit × the label positions where no variable of the subgroup says "ogółem"; DBW
measure = indicator × presentation, the territorial dimension is the one whose positions match
areas; NBP measure = table × rate type with the currency as breakdown.

Known data findings surfaced by the PoC (for Silver, not Gold): a BDL subgroup can hold the
same series under its website code and its API id, sometimes with different values (#868) —
the PoC keeps the API row; BDL publishes Mazowieckie as a macroregion and as a voivodeship —
the PoC keeps the voivodeship; the web export gives the Górnośląsko-Zagłębiowska Metropolia
the code of Śląskie — a row whose unit name disagrees with its id's name is treated as an
unmatched unit of its own; about 1,700 BDL unit ids (mostly gmina parts, 12-character ids) and
a few DBW city podregions do not map by name (`map_geography.matched = false`,
`build_check.rows_geography_unmatched`) — v1 uses the GUS KTS–TERYT table; two activated
blocks yielded no rows in the trials — `build_check` shows them with their catalogue status:
BDL P2137 Ludność is `waiting` (not landed yet, the BDL fill is running) and Eurostat UNE_RT_M
is loaded but its sample filter (unit `PC_ACT`, age `Y15-74`) matched nothing: check the
dataset's codes before relying on the monthly unemployment concept member.

## How to build

- **Trial against real Silver, scratch namespace** `zz_dev_poc`: Dev workflow, script
  `poc_trial` on a branch (`dev/poc_trial.py` in the history of branch `feat/gold-poc`;
  `dev/` never lives on main; `--drop` removes the scratch tables). It runs the prod target
  with the dbt var `poc_schema: zz_dev_poc` (the poc folder's schema, `dbt_project.yml`) and
  `--select poc`, so the PoC is written to the scratch namespace and reads the real Silver and
  Gold tables. The last trial (run 40319860060, 26 Oct) built the 30 models in 3.5 minutes with every test passing.
- **Big Silver tables are read by Python models** (`poc_src_eurostat.py`, `poc_src_dbw.py`,
  `poc_src_dbw_dictionary.py`): the planner lists the activated blocks' files from the
  Iceberg metadata and DuckDB streams only those; the dbt SQL path scanned every file of
  `silver.eurostat_observations` (19 bn rows) and never finished. This is the per-block
  builder of v1 in its simplest form.
- **Production** (`poc` namespace): Pipeline run "silver/gold: build models", source
  `platform`, filter `poc`. The scheduled build rebuilds the PoC when its inputs change
  (the Python models declare theirs with `dbt.source`), like any model; because
  `gold.coverage` changes on every source run and `silver.bdl_observations` on every BDL
  run, expect the PoC (3–4 minutes) in most daily builds. Annotations show the row
  ceilings; `poc.build_check` the data quality; `tests/poc_fact_grain.sql` fails on a
  duplicate series × period.
- **Local** (no credentials): fake Silver in DuckDB from the column lists of the models; see
  the harness in the session that built the PoC (`dbt build --select poc` on a local profile).

## Checks after a build (`poc.build_check`)

`rows_geography_unmatched` per block (BDL 12-character ids and DBW podregion names are the
likely ones), `rows_total_series` > 0 for every measure a concept uses, `frequencies` as
declared, `first_date`/`last_date` plausible. `dim_measure` rows with `status <> 'activated'`
are the blocks the owner can activate next.

## Semantic layer and BI

`warehouse/semantic_models/poc.yml`: one MetricFlow semantic model per metrics table and one
metric per concept. For Power BI the metrics tables are the fact tables and `dim_calendar`,
`dim_geography`, `dim_source` the shared dimensions; `dim_measure` + `measure_dimensions` is
the explorer's catalogue. Fabric can reach the Iceberg Parquet files through an S3-compatible
shortcut to the R2 bucket (`STORAGE_LAKEHOUSE_CATALOG_NAME` path, namespace `poc`).

## Open points for v1 (design decisions 1–8 in the design doc)

- geography: BDL 12-character ids and DBW names are mapped by name here; v1 uses the GUS
  KTS–TERYT correspondence table and NUTS 3 ↔ podregion;
- the measure-defining rule per domain (Eurostat `indic_*`, BDL n1, DBW presentation);
- descriptions (Eurostat ESMS, BDL subject tree, WDI definitions) in `dim_measure`;
- deterministic hash keys, block-wise builds with `entity_tables`, rows without a value;
- the remaining frequencies (Q, S, W), sex/age/activity as conformed tables, registries.
