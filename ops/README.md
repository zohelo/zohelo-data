# Ops: standing operational tasks

Scripts here are run by the **Ops · ad-hoc** workflow (`ops.yml`) from `main`: defined
tasks the owner may want to run again from time to time. One script per run, with the
R2 credentials, by manual dispatch or by a row of the schedule table below. Scripts that change anything do so only with an
explicit flag (`--apply`, `--delete`); without it they only report.

Not for experiments, trials or one-off fixes: those are `dev/` scripts on a feature
branch, run with **Dev · branch runs** and deleted before the merge. Recurring table
maintenance (compaction, snapshot expiration) is an R2 Data Catalog setting, not a
script (`catalog_maintenance --apply` sets it to the data policy). The catalog does not
expire snapshots of tables without new commits; `expire_snapshots --apply` applies the
same policy to those.

| `platform_inventory` | Per source: Landing / Archive files, GB and latest write; Bronze / Silver / Gold tables, rows, files, GB (from the snapshot summary, or the manifests when a writer left the totals out); total snapshots. Storage per bucket and folder with a monthly cost estimate (R2 Standard beyond the 10 GB free tier; warning above $2); tables and Landing folders no source claims; registered tables that do not exist. Doubles as the connectivity check. Args: `--source <id> …` | nothing |

| `backlog_sync` | The backlog engine (`docs/backlog.md`). Mode `validate [--root DIR …]` (standard library and pyyaml only; also run in zohelo-bi and zohelo) checks `.github/backlog/` (areas, stages, epics) and the Epics generated from `ingestion/register.yaml` and `stages.yaml` for every register entry without an `epics/src-<id>.yaml` file (needs `family`; entries without it are listed in a warning; prints `file sources`, `generated sources` and `register entries without family`): keys, parents, required fields, enums, title lengths, dependencies, and for open Tasks the files, steps, acceptance, verify and size rules. Prints `file: key: message` per error and exits 1, else `ok: N areas, N epics, N deliverables, N tasks`. An edit/delete path that no longer exists (a merged PR before its Task is marked done) is a warning; with `--strict` (backlog sync) it is an error. Run locally: `python -m ops.backlog_sync validate`. Mode `render KEY [--root DIR …]` prints the title, labels and issue body of one node (the renderer the sync uses and the 3 KB Task limit measures). Modes `plan` and `apply [--root DIR …]` (roots: this repository plus `_repos/zohelo-bi` and `_repos/zohelo` when present) match the nodes with the issues of the three repos by the key in the first body line. `plan` only reads and annotates, per repo, `to create / to update / to reparent / to close`; `apply` creates (done Tasks and Deliverables are closed with a comment), updates title, labels, type and the body above the notes marker, sets parents, and closes issues whose key left the files (`not_planned`); both modes also read project 1 and add every synced issue to it (`addProjectV2ItemById`, idempotent) and set Product, Phase, Priority, Effort and Target date from the files where the value differs (Status and Sprint stay with automation and planning; fields or options the project lacks are listed in a warning), annotating `project items: N to add, M fields to set` (plan) or `added` / `set` (apply); at most 400 writes per run, 1 s apart (rerun continues); refuses while `.github/backlog/migration.yaml` lists an `adopt` key without a marked issue; warns when more than 3 `owner:action` issues are open. Token: `GH_PROJECT_TOKEN`, `GITHUB_TOKEN` or `GH_TOKEN` (issues read for plan, write for apply). Mode `migrate [--apply]` (#975) migrates the old issues listed in `.github/backlog/migration.yaml`: `adopt` puts the key marker as the first body line with the rendered head, sets title, type and (when it exists) parent, and keeps the old body below the notes marker; an adopted alert (type Bug) gets type and its source Epic as parent, no key; `close` comments the replacement and closes as not planned. Without `--apply` it annotates `to adopt / alerts to type / to close / already migrated / remaining`; with it, at most 400 writes per run (rerun until `remaining` is 0; done issues are skipped); labels, project fields and missing parents are left to `apply`. Mode `pr-check` (standard library only; run by the `check` job and, at a pinned commit, in zohelo-bi and zohelo) reads the pull request event and passes when the body has `Closes #n` (or `Closes zohelo/<repo>#n`) for an open Task or Bug without the `verify-only` label; Dependabot pull requests are skipped. | nothing |

**Scheduler clock runbook.** Setup or credential change: Ops `script=scheduler_trigger args=deploy`
(code, Cron Triggers, and the Worker secrets APP_CLIENT_ID / APP_PRIVATE_KEY from the organisation
variable `ORG_BOT_CLIENT_ID` and secret `ORG_BOT_PRIVATE_KEY`); `args=status` then shows
`app_credentials_set: true`. The Worker dispatches as the organisation's GitHub App
(zohelo-automation, installation token limited to this repository with Actions: write), so no
personal token is involved and nothing expires. Pause: Ops `script=scheduler_trigger args=pause` (GitHub's own
schedule keeps running as the backup; a later `deploy` restores the Cron Triggers). Resume:
`args=resume`. A failed dispatch shows in the Worker's Cron events and as a drop in scheduler
runs. Scheduler runs started by the Worker
are workflow dispatches named `Pipeline · platform · scheduler: dispatch due runs`.

**Key rotation runbook.** Before rotating storage or catalog keys (organisation secrets
`STORAGE_*`), pause the scheduler: Ops `script=scheduler_trigger args=pause`; rotate; check
with one manual run (e.g. Ops `platform_inventory`); then `args=resume`. GitHub's backup
schedule still fires while paused, so a run may fail with `Unauthorized` inside the window
and open an `alert` issue: close it with the note "rotation window" once that source's next
run is green.

**Schedule table.** `ops.yml` also runs on `schedule`. Its first job `resolve` picks the script and
arguments: for a manual dispatch the inputs, for a scheduled run the row of a `case "$CRON"` table that
matches the cron (an unknown cron fails the run, so no schedule can silently run another schedule's
script). To schedule a script, add the cron under `on.schedule` and a row to that table; the concurrency
group is `zohelo-ops-<script or cron>`. Rows: `20 5 * * 1` (Mondays 05:20 UTC) runs `orphan_files --delete
--min-age-hours 48` (orphans re-accumulate after failed commits and dropped tables; `--max-share` stays 0.5).
Row `0 5 * * 1` (Mondays 05:00 UTC) runs `backlog_sync apply`: GitHub issues and the project follow the `.github/backlog/` files of the three repositories.
Row `5 6 * * *` (daily 06:05 UTC) runs `scheduler_trigger heartbeat`: fewer than 40 Worker dispatches (of 48 a day)
in the last 24 h fail the run, and the run then opens or updates the alert issue "Pipeline failed: scheduler · heartbeat"
(`ops.notify_failure`), so a stopped Worker reaches the owner.
Scheduled runs are never `branch_cleanup` (its job runs on manual dispatch only).

Rules: one file per script (a script's deployable assets may sit in a folder of its own, like `scheduler_worker/`), `snake_case.py`, runnable as `python -m ops.<name>`. Write
output files to `$OPS_OUTPUT_DIR` (kept 7 days as a run artifact) and publish results as
annotations (`ingestion.common.report.annotate`; GitHub shows at most 10 per step). List
every script here; remove it when the task no longer exists.
